# Nick's Pizza: spec

What to build for v1. `AGENTS.md` holds the rules; this file holds the decisions. When something here is still open, it's listed under Open questions: ask instead of guessing.

## The shop

Nick's Pizza is a classic neighbourhood pizzeria with pizza, subs, wings, burgers, salads, sides, drinks and dessert. Prices are in USD. There is no tax or tip in v1. Every order is pickup or delivery, and delivery adds a flat $3.99 (see "Pickup or delivery").

## Menu

30 items. `menu.json` holds them in this shape:

```ts
type MenuItem = {
  id: string
  name: string
  category: 'pizza' | 'subs' | 'wings' | 'burgers' | 'salads' | 'sides' | 'drinks' | 'dessert'
  description: string
  tags: Array<'vegetarian' | 'vegan' | 'spicy' | 'popular'>
  variants: Array<{ id: string; label?: string; price: number; serves: number }>
  pairsWith: string[]
  spokenName?: string
}
```

- `price` is in cents.
- An item with one size has one variant whose `id` equals the item `id` and that has no `label`.
- A sized variant's `id` is `<item-id>-<size>` (`pepperoni-pizza-large`).
- `pairsWith` lists item ids. The agent uses them for suggestions. They're sides, drinks and the like, never a main (a pizza or a sub): a suggestion card holding a group plan's main counts as a change to that plan (see Decisions), and `menu.test.ts` checks it.
- `spokenName` is how the agent says the item in a sentence, when its name doesn't read well aloud: `"garlic knots"` for "Garlic Knots (6)". Without it, the name in lower case.
- `serves` is how many people one of that variant feeds. The group-order planner (`plan_group_order`) uses it:

  | Variant | Serves |
  |---|---|
  | Large pizza | 4 |
  | Medium pizza | 2 |
  | Wing Dings 12 pc | 4 |
  | Wing Dings 6 pc | 2 |
  | Garlic knots, fries, mozzarella sticks | 2 |
  | Sub, sandwich, burger, salad, drink, cannoli | 1 |
- One function turns the menu into the flat product list the cart and `validateCartItems` use: one product per variant, `{ id, name, price, currency: 'USD' }`. Its `name` includes the size ("Large Pepperoni Pizza").

## Tools

The menu goes into the agent's instructions in compact form (ids, names, sizes, prices, `serves`, tags, `pairsWith`), so the agent can resolve "a large pepperoni" to an id and make suggestions on its own. Tools exist where they change state or change the screen.

Every cart tool returns the cart summary:

```ts
type CartSummary = {
  lines: Array<{ id: string; name: string; quantity: number; total: string }>
  count: number
  total: string       // "$46.97", for the screen
  totalSpoken: string // "forty-six ninety-seven", what the agent says (see Decisions)
  delivery?: {        // only for delivery, with something in the cart: what Stripe adds (see "Pickup or delivery")
    fee: string                     // "$3.99"
    feeSpoken: string               // "three ninety-nine"
    totalWithDelivery: string       // "$50.96"
    totalWithDeliverySpoken: string // "fifty ninety-six"
  }
}
```

| Tool | Parameters | Does | Returns |
|---|---|---|---|
| `find_menu_items` | `category?`, `tags?`, `max_price?` (dollars), `query?` | Filters the menu and highlights the matching cards on screen | matching items with their variants and prices, and when something matched, `note`: they're lit up, so name two or three and don't show them again |
| `show_suggestions` | `title`, `items: Array<{ id, quantity }>`, `reason?` | Opens the suggestion card (see Screens). It doesn't change the cart. | `{ shown: true, total, totalSpoken, delivery? }` (the total if every suggestion were added; `delivery` only for a change to a group plan still on screen, for a delivery order) |
| `plan_group_order` | `people`, `vegetarians?`, `budget?` (dollars), `preferences?: { mains?: 'pizza' \| 'subs' \| 'mix', spicy?, drinks?, include?: item ids }` | Works out a plan for the group from `menu.json` (`planGroupOrder`), leaving room for what's in the cart and, with a budget, made leaner to fit it (the delivery fee counted unless it's pickup), and opens it on the suggestion card, as `show_suggestions` does. It doesn't change the cart. | `{ shown: true, note, summary, budget?, total, totalSpoken, delivery?, lines }` (`note`: the card shows it, so don't show it again; `summary`: "8 large pizzas, 3 of them vegetarian, plus garlic knots and a drink each"; `budget`: what it took to fit; `delivery`: for delivery, as the cart tools give it) |
| `add_item` | `id` (variant id), `quantity` (1–20) | `addItem` | `CartSummary` |
| `add_items` | `items: Array<{ id, quantity }>` (up to 15 lines) | `addItem` for each line, in one call | `CartSummary` |
| `set_quantity` | `id`, `quantity` (1–20) | `setItemQuantity` | `CartSummary` |
| `remove_item` | `id` | `removeItem` | `CartSummary` |
| `view_cart` | none | reads the cart | `CartSummary` |
| `clear_cart` | none | `clearCart` | `CartSummary` |
| `set_order_type` | `type`: `'pickup' \| 'delivery'` | records pickup or delivery (see "Pickup or delivery"); the cart drawer shows it. It doesn't change the cart. | `{ orderType, cart? }`: `cart` is the cart line with the total (and, for delivery, the total with the fee), only when the cart isn't empty |
| `checkout` | none | starts checkout for pickup or delivery (see Checkout) | `{ ok: true, total, totalSpoken }`, the amount to pay on Stripe's page (for delivery, the total with the fee), or a recovery message |

- Parameter `id` is an enum of every variant id, generated from `menu.json`.
- Recovery messages are short and offer a next step:
  - **Unknown id:** "That's not on the menu. Close matches: …"
  - **Sized item without a size:** "Pepperoni comes in medium or large. Which one?"
  - **Item not in the cart** (for `set_quantity` or `remove_item`): "That isn't in the cart. The cart has: …"
  - **Checkout with an empty cart:** "The cart is empty."
  - **Checkout before pickup or delivery is chosen:** "Ask whether it's pickup or delivery first."
  - **`set_order_type` with anything else:** 'The type has to be "pickup" or "delivery". Ask which, if the customer hasn't said.'
- `find_menu_items` highlights stay until the next search or until the customer scrolls or clicks a card.
- `add_items` checks every line before adding any. If one id is unknown, nothing is added and the recovery message names the bad line.

### Suggestions and group orders

- **"What goes well with X?"** The agent answers from X's `pairsWith`, then calls `show_suggestions` with those items so they appear on screen.
- **"What do you recommend?"** The agent picks from items tagged `popular` and shows them the same way.
- **Group orders** ("I've got a party of 20"):
  1. The agent asks one short question at most, covering what matters ("Any vegetarians, and pizza, subs or a mix?"), and none if the customer already said. Then it calls `plan_group_order` with the head count, the vegetarians and what the customer said. The code does the math from `serves` (the rules are under Decisions), not the agent.
  2. As the plan starts, the agent says "Let me put something together." (the same words every time; the app sends them). The plan opens on the suggestion card, titled "For your party of 20" with a one-line reason. The agent presents it in one short sentence, the way a person would ("Five large pizzas, garlic knots and a soda each"), says the total from the tool result, and that it's on screen. While presenting it, before anything is added, it never reads out every line or does arithmetic aloud.
  3. It adds the plan with `add_items` only after the customer agrees ("yeah, add all that"), then confirms every line it added, with quantity, size and name, and the new total, as after any change: the owner wants every line read back. Or the customer taps **Add all to cart**.
  4. Changes before agreeing ("swap one pepperoni for a veggie") update the card with another `show_suggestions` call.
  5. A budget ("we've got about $250"), before the plan or after it, goes to `plan_group_order` as `budget`. The plan comes in at or under it, the delivery fee counted unless it's pickup, made leaner in the owner's order (see Decisions), and the agent says in a few words what it took ("cheaper pizzas and drinks for 17 of the 30") and the total. If even the leanest plan costs more, the agent says the least it can be and asks.

## Agent instructions (first draft)

Greeting, built when the customer presses the talk button: "Hey, welcome to Nick's Pizza! Is this for pickup or delivery?", or once they've chosen (in the cart, or in an earlier session) "Hey, welcome to Nick's Pizza! Still delivery today?" (or "pickup"). A session without `set_order_type` greets "Hey, welcome to Nick's Pizza! What can I get started for you?"

```text
You work the counter at Nick's Pizza, a classic neighbourhood pizzeria. You're friendly and quick, like someone who's done this a thousand times.

Keep every reply to one or two short sentences. This is a voice conversation: no lists, no markdown, and say prices the way people do ("eighteen ninety-nine").

You only know this menu: {{MENU}}

Rules:
- Every order is pickup or delivery. When the customer says which, call set_order_type, then say one short line like "Great, delivery it is. What can I get you?", or if they were checking out, call checkout next. If they order something before saying which, add it with its tool right away and confirm it as usual, then ask "Pickup or delivery?" once, in the same reply; never hold an item until they answer, or promise to add it later, and don't call set_order_type until they say which. For delivery, never take an address by voice: if one comes up, say "You'll enter the delivery address at checkout." If asked about fees, delivery adds a flat three ninety-nine at checkout.
- To change the cart, always use a tool, and say nothing about the change, not even its price, until it returns. Never claim you added, changed or removed something unless the tool returned it.
- After each change, confirm it from the tool result: the quantity, size and name of every line you added or changed, then the new total, for delivery with the fee named. After add_items, name every line it added, one by one ("two large cheese pizzas, three large pepperoni pizzas, six garlic knots, …"), a whole group plan included, even if it takes more than two sentences; never sum them up.
- Say every total exactly as the totalSpoken in the tool result gives it, word for word, even a long one ("two hundred ninety-seven dollars and fifty-six cents"); never turn the digits in total into words yourself.
- For delivery, a cart or a plan in a tool result also has delivery. Every time you say its total, after a change too, name the fee and give the total with it, each word for word: "forty-one ninety-eight, plus three ninety-nine for delivery, forty-five ninety-seven in all" (totalSpoken, feeSpoken, totalWithDeliverySpoken).
- If a sized item has no size, ask which size before adding it.
- Use find_menu_items when the customer asks what you have that matches something ("vegetarian", "spicy", "under ten bucks"), so the matching items light up on screen. Then name two or three of them. They're lit up already, so don't call show_suggestions for them.
- When you suggest specific items, call show_suggestions so they appear on screen, and keep your spoken answer short: the screen shows the details.
- When asked what goes with something, call show_suggestions with the items in its pairsWith, one of each, titled like "Goes with the Classic Cheeseburger", then name them in one short sentence. When asked what you recommend, unless it's for a group, do the same with two or three popular items, titled "Our favourites". Never name pairings or recommendations without showing them.
- For a group, if the customer hasn't said what they like, ask one short question that covers it, such as "Any vegetarians, and pizza, subs or a mix?", then call plan_group_order with what you know. Never ask a second question before the plan. When you call plan_group_order, say nothing with it: "Let me put something together." is said for you while it plans. To present the plan, before anything is added, sum it up from its summary in one short sentence, the way a person would ("Eight large pizzas, three of them veggie, plus garlic knots and sodas"), then say its totalSpoken (for delivery, with the fee, as every delivery total) and that it's on screen; don't list its lines or do the math out loud. If they give a budget, before the plan or after it, call plan_group_order with it, then say in a few words what it took to fit, from the result's budget, and the total. The plan is already on screen, so call show_suggestions only when the customer asks to change it ("swap a pepperoni for a margherita"), with the changed lines. Add it with add_items only after they agree, then name every line it added, one by one, as after any change.
- Offer one pairing on your own at most once per order, after the first item is added, in one short question. When the customer asks for suggestions, always help.
- If asked about something not on the menu, say you don't have it and offer the closest thing you do have.
- If the conversation goes off topic, answer in one friendly line and steer back to the order.
- The customer can also change the cart by tapping. Before answering anything about what's in the cart or the total, call view_cart and answer from its result.
- When the customer is done, read back the order and total from view_cart, then call checkout when they confirm, and when it returns ok, say "Taking you to checkout now so you can pay", then the totalSpoken it returned, word for word (for delivery it already has the fee in it), then, for delivery only, "and enter your delivery address", as one sentence: for pickup "Taking you to checkout now so you can pay forty-one ninety-eight.", for delivery "Taking you to checkout now so you can pay forty-five ninety-seven and enter your delivery address." Never say the order is placed, done or confirmed: it isn't until they pay.
```

`{{MENU}}` is filled in from `menu.json` when the session starts. The instructions end with the order as it is then: "Conversation started. Order type: delivery. Cart: 1 × Large Pepperoni Pizza. Total $20.99, $24.98 with delivery." ("Order type: not chosen yet." before the customer chooses; for pickup, or before choosing, the total alone). The instructions live in their own module, next to the tool definitions.

## Voice session

- Connection settings (listen model, think provider and model, speak voice) use whatever Deepgram's current docs recommend for a low-latency voice agent. Write the chosen values into this file under Decisions once picked.
- The talk button connects on press. Pressing it again, or leaving the page, ends the session.
- Live captions above the button show the customer's last line and the agent's current reply. This makes it clear what the agent heard. A toggle above them opens the whole conversation (see Decisions).
- The session ends on its own after 60 seconds with no speech from either side.

### The agent always works from the current cart

The customer can change the cart by clicking at any time, including mid-conversation. The agent must never answer from a stale cart:

1. A session starts with pickup or delivery and the current cart summary in the agent's instructions.
2. While a session is open, every click that changes the cart, or chooses pickup or delivery, sends the agent a short context update ("Customer added 1 × Fries by tapping. Order type: delivery. Cart: …", "Customer chose delivery by tapping. Cart: …"). Use the Voice Agent API's message for updating context mid-session; check the current docs for which one.
3. The agent calls `view_cart` before answering anything about what's in the cart or the total. The tool reads the live cart, so the answer is right even if an update was missed.

Check: add fries by clicking while a session is open, then ask "what's my total?" The answer includes the fries.

## Pickup or delivery

The owner chose this on 2026-11-10 (`.build/step-5b.md`). Every order is pickup or delivery, and checkout needs to know which.

1. The greeting asks: "Hey, welcome to Nick's Pizza! Is this for pickup or delivery?" The customer says "Delivery." The agent calls `set_order_type` and says one short line: "Great, delivery it is. What can I get you?" If the customer already chose (in the cart, or in an earlier session), the greeting asks to confirm it: "Still delivery today?" If the customer orders before choosing ("Add a large cheese pizza"), the agent adds it at once, confirms it, and asks "Pickup or delivery?" in the same reply; it never holds an item until they answer.
2. The cart drawer has a **Pickup | Delivery** switch above Checkout, showing the choice. Choosing by tap tells the agent during a session ("Customer chose delivery by tapping. Cart: …").
3. Checkout refuses until it's chosen: the `checkout` tool answers "Ask whether it's pickup or delivery first.", and the Checkout button shows "Choose pickup or delivery first." without calling the server.
4. No address by voice. Stripe's page asks for the delivery address (US only) and adds the flat $3.99 fee, and asks for a phone number either way (see Checkout). The agent says "You'll enter the delivery address at checkout." if an address comes up, and, checking out a delivery order, "Taking you to checkout now so you can pay forty-five ninety-seven and enter your delivery address.", with the total with the fee that `checkout` returns.
5. For delivery, every cart the tools return (the cart tools and `view_cart`) also has the fee and the total with it, written and spoken (`delivery` in `CartSummary`), so the total the agent says is what Stripe charges: "forty-one ninety-eight, plus three ninety-nine for delivery, forty-five ninety-seven in all". The cart line that ends the instructions and every tap update give it too, in digits: "Total $41.98, $45.97 with delivery." Pickup's totals are as before.
6. The choice is saved in the browser next to the cart, so a reload keeps it, and it's forgotten with the cart once the customer has paid.

## Checkout

1. The `checkout` tool, or the Checkout button in the cart drawer, calls the server function `createCheckoutSession({ cartDetails, orderType })`, where `orderType` is `pickup` or `delivery`.
2. The server runs `validateCartItems(products, cartDetails)` and re-checks the order type (`isOrderType`), then `stripe.checkout.sessions.create` with `mode: 'payment'`, the validated line items, and:
   - `success_url`: `<origin>/order/success?session_id={CHECKOUT_SESSION_ID}&type=<pickup|delivery>`
   - `cancel_url`: `<origin>/?checkout=cancelled`
   - `phone_number_collection: { enabled: true }`, for both: Stripe's page asks for a phone number.
   - Delivery only: `shipping_address_collection: { allowed_countries: ['US'] }` (`DELIVERY_COUNTRIES`), and one `shipping_options` entry, a `fixed_amount` rate of $3.99 (`DELIVERY_FEE`) named "Delivery". Stripe's page asks for the address and shows the fee as its own line.
3. The server returns `{ url }`, and the `checkout` tool returns `{ ok: true, total, totalSpoken }`: what Stripe will charge for the cart it sent, from `summarizeCart`, so for delivery the total with the fee. A validation failure returns a message, which the tool passes back to the agent. Without pickup or delivery the message is "Choose pickup or delivery first.", and Stripe isn't called.
4. From voice, the agent says the amount from the tool's `totalSpoken`: "Taking you to checkout now so you can pay forty-one ninety-eight.", or for delivery "Taking you to checkout now so you can pay forty-five ninety-seven and enter your delivery address." (`checkoutLine` in `src/agent/tools.ts`). Every path to Stripe by voice ends on this line, so the customer always hears what they'll pay. It never says the order is placed: nothing is ordered until they pay. Once it finishes speaking, the client closes the voice session and calls `redirectToCheckout(url)`.
5. The success page says the order was received (test mode), shows the order number from the session, then "Ready for pickup in about 20 minutes." or "Out for delivery soon." from the url's `type` (neither when it's missing), and clears the cart. The cancelled state shows a small notice, and the cart stays as it was.

Test card: `4242 4242 4242 4242`, with any future date and any CVC.

The cart drawer opens on its own the first time a voice change adds an item, so the change is visible; on phones the order strip shows it instead (below).

**The order board.** The cart drawer works like a drive-thru's order board, in the page's own light style: the lines a change adds key in one by one, each lit up (a warm yellow with a red edge) as it lands. What the agent adds keys in as it reads the lines back, the first once its voice starts and each next one about as long after as saying the one before takes; what the customer taps keys in about a third of a second apart; a changed quantity lights its line up again; a line taken out is struck through and fades. The total is the cart's, so the board never shows less than Checkout charges. A tap made while the agent's lines key in shows at once. During a voice session the drawer opens with the agent's voice, as its first line keys in, and says the cart is empty only when it is. A cart loaded from the browser's storage just shows as it is.

**Pickup or delivery.** A two-option switch across the bottom of the cart, above the total and Checkout: a radio group drawn like the menu cards' size picker, each option at least 44 px tall. Neither is selected until the customer chooses, by tapping it or by telling the agent. With Delivery selected, a line under it says the address is entered at checkout and delivery adds $3.99, and a **Delivery $3.99** line sits above the total, which then includes the fee: what Stripe will charge, and what the agent says. Both figures come from `summarizeCart(quantities, 'delivery').delivery` (`fee`, `totalWithDelivery`), as the tools get them. It shows with an empty cart too, since the agent asks it first. Checkout pressed without a choice shows "Choose pickup or delivery first." above the button.

**Suggestion card.** `show_suggestions` slides a card up above the talk button. It's a sheet, not a blocking modal: the menu stays visible behind it, and the conversation keeps going. It reads as a suggestion, not the cart. During a voice session it comes up once the agent has started talking, not before (see Decisions).

        ┌───────────────────────────────────┐
        │ OUR SUGGESTION                    │
        │ For your party of 20           ✕  │
        │ Mix of favourites, two veggie pies │  reason
        │ 4 × Large Pepperoni Pizza  [Add]  │
        │ 2 × Large Veggie Supreme   [Add]  │

- Each line shows the item's name, size, quantity and price. **Add** adds that line. **Add all to cart** adds every line with the same logic as `add_items`.
- The card closes on ✕, after **Add all to cart**, or when the agent shows a new set of suggestions (the new set replaces it).
- A small pairing suggestion (one or two items) uses the same card.

**Phones.** The layout works from 360 px wide up:
- Menu cards stack in one column.
- The cart drawer becomes a full-screen sheet. A voice change doesn't open it, since it would cover the menu: an **order strip** above the talk button shows "YOUR ORDER", the last line keyed in, changed or taken out, lighting up as the board keys lines in, and the cart's total. Tapping it opens the cart. It shows while the cart is closed and a line is in, and the suggestion card sits above it.
- The suggestion card spans the screen width above the talk button.
- The talk button stays reachable with a thumb and never covers the cart's Checkout button.

Test the golden path at phone width in the browser's device mode as well as at desktop width.

**Images.** Each menu item has a real food photo, stored in the repo under `public/images/` and never linked from another site. The rules:

## Decisions

Record decisions made during the build here (voice settings, library choices, anything this file left open), with one line on why.

- **TypeScript pinned to `~6.0.3`.** typescript-eslint 8.x supports only `typescript <6.1.0`; TypeScript 7 would break linting.
- **`compatibility_date` is `2026-11-08`.** The workerd bundled with `@cloudflare/vite-plugin` refuses newer dates, so `pnpm dev` would not start.
- **Secret names are listed in `wrangler.jsonc` under `secrets.required`.** Names only, never values. `wrangler types` then gives the same output with or without `.dev.vars`, and deploy fails until both secrets are set.
- **Generated files are committed** (`src/routeTree.gen.ts`, `worker-configuration.d.ts`), so `pnpm check` works on a fresh clone without running dev or `wrangler types` first.
- **Vitest has its own `vitest.config.ts`** without the Cloudflare or Start plugins: tool handlers and other logic are tested as plain Node functions.
- **Lint, typecheck and tests use ESLint, TypeScript and Vitest.** ESLint runs a flat config with `@eslint/js`, `typescript-eslint` and `eslint-plugin-react-hooks`. Step 1 requires all three checks and these are the TanStack and Vite defaults, but they sit outside the AGENTS.md stack table, so the owner should confirm them, together with `@types/node` (Node types for `nodejs_compat` code and config files) and `@vitejs/plugin-react` (required by TanStack Start's Vite setup).
- **`observability.enabled: true` in `wrangler.jsonc`.** Workers logs are on so a deployed copy can be debugged from the dashboard; it's the Cloudflare template default.
- **Currency and locale live in `src/shop.ts`** (`CURRENCY`, `LOCALE`). `CartProvider`, the product list and `formatPrice` all read them, so a shop in another currency edits one file and server and browser format prices alike. The agent's spoken totals (`src/agent/spokenPrice.ts`, below) are English and US dollars, so a shop in another currency or language rewrites that file too.
- **No formatter in `pnpm check`.** Step 1 asks for lint, typecheck and tests only, and Prettier or Biome would be another dependency outside the stack table. Add one if the owner wants it.
- **Categories live in `src/menu/menu.ts`.** SPEC fixes `menu.json` as a list of items; `categories` sits next to it and defines which category ids exist, how they're shown (order, label, note) and what each is in a group plan: `plan` is `main`, `side` or `drink` (none: not planned), and a main category's `noun` is how a plan counts it (`['pizza', 'pizzas']`). The planner's categories, its summary's nouns and the `mains` choices in `plan_group_order`'s schema (each main category, plus `mix`) are built from them, so a shop with other mains edits this list, not the planner. The type makes a main category without a `noun` fail typecheck.
- **An item can have a `spokenName` in `menu.json`,** for a name that doesn't read well aloud: "garlic knots" for "Garlic Knots (6)". Without it, the agent's words use the name in lower case (`spokenName()` in `menu.ts`). The planner used to strip a trailing parenthetical with a regex, which assumed every such name could lose it; now the data says so. It extends SPEC's `MenuItem` shape by one optional field, which `menu.test.ts` allows.
- **Menu cards start on the size that feeds the most people** (Large, 12 pc), via `defaultVariant`: the common order is one tap away; the SPEC sketch's mixed defaults were illustrative.
- **Clicks share the voice tools' cap of 20 per line** (`MAX_LINE_QUANTITY` in `src/shop.ts`): Add and + stop at 20, so a line the agent reads back never exceeds what its tools accept.
- **use-shopping-cart is pinned to `4.0.0-rc.3`, and pnpm installs new releases right away.** pnpm 12 waits 24 hours before installing a newly published version (`minimumReleaseAge`), which held the project on rc.2. The owner turned the wait off with `minimumReleaseAge: 0` in `pnpm-workspace.yaml`, so new release candidates can be tried the day they ship.
- **Photos are found by item id** (`public/images/<item-id>.jpg`, via `imagePath`), so the SPEC's `MenuItem` shape needs no image field.
- **Sized product names put the size first:** variant labels are `Medium`/`Large` and `6 pc`/`12 pc`, and the product is "Large Pepperoni Pizza" or "12 pc Buffalo Wing Dings". One rule, in `productFor`.
- **A click on Add doesn't open the drawer.** The button says "Added ✓" and the badge updates; SPEC opens the drawer on its own only for voice changes.
- **The drawer is a custom sheet, not a native `<dialog>`.** While it's open only the page wrapper is `inert`, so the step 4 talk button can live outside it and stay usable mid-conversation. The panel is `role="dialog"` without `aria-modal`, which would also hide the talk button, captions and voice errors from screen readers; `inert` already keeps the page behind out of reach. Open/closed is the cart library's `shouldDisplayCart`.
- **System font stacks, no web fonts.** A bold serif stack for headings and a sans stack for text keep the page free of third-party requests.
- **The Stripe client is built with `httpClient: Stripe.createFetchHttpClient()`.** Stripe's docs and README say nothing about Workers. stripe@23's `workerd` export already defaults to fetch, and Cloudflare's own Stripe guide passes the fetch client, so passing it explicitly keeps the code working whichever build gets resolved.
- **Checkout reads only ids and quantities from the posted cart** (`src/checkout/checkout.ts`). It checks each line (on the menu, quantity 1–20) before `validateCartItems`, so the message can name the line. Passing only ids and quantities also keeps out the browser's `product_data.metadata`, which `validateCartItems` would otherwise copy (see `LIBRARY_FEEDBACK.md`).
- **Stripe's return urls use the request's own origin** (`getRequest().url`), not `x-forwarded-*` headers, so local dev and every deployed hostname work without configuration.
- **The order number is the last 8 letters and digits of the Checkout Session id, uppercased** (`orderNumber`). The success page already has the id in its url, so showing the number takes no Stripe call. It's for people to read; the full id finds the order in the dashboard.
- **The order page clears the cart whenever its url has a `session_id`, without asking Stripe if it was paid.** Stripe sends customers there only after paying, and a hand-typed url can only empty the visitor's own cart. Without a `session_id` it says there's no order to show and leaves the cart alone.
- **The order page has a small header of its own** (the brand, linking home) instead of `SiteHeader`: the cart it would open was just emptied, and its category links point at sections on the menu page.
- **Pickup or delivery changes only what Stripe's page asks for** (`checkoutCart` in `src/checkout/checkout.ts`; the settings are in `src/shop.ts`). The owner chose this on 2026-11-10 (`.build/step-5b.md`). Both ask for a phone number (`phone_number_collection`), so the shop can reach the customer. Delivery adds Stripe's address form, US only (`DELIVERY_COUNTRIES`), and the flat $3.99 fee (`DELIVERY_FEE`) as one fixed-amount shipping option named "Delivery", which Stripe shows as its own line and adds to the total. The fee isn't a cart line, so the cart is the same for both. The server re-checks the order type the browser posts (`isOrderType`) and, without one, answers "Choose pickup or delivery first." without calling Stripe. The type rides on the success url (`&type=delivery`), so the order page can say "pickup" or "delivery" without asking Stripe, and the server keeps its two jobs; a missing or unknown type shows the page as before. **No address by voice:** speech-to-text garbles street names and house numbers, reading an address back is slow, and Stripe's form autocompletes and checks it, so the agent asks pickup or delivery and Stripe asks where.
- **The Checkout button stays pending until the browser leaves for Stripe**, and clicks while pending do nothing, so a second click can't start a second session. It's `aria-disabled`, not `disabled`, so it keeps focus and screen readers hear "Taking you to checkout…". It resets on `pageshow` when the browser's Back button restores the page from the back/forward cache.
- **Tests that load the route tree mock `cloudflare:workers`** (`src/router.test.ts`): routes reach the server functions, which import it, and only workerd has that module.
- **The tools live in `src/agent/`:** `tools.ts` (definitions), `handlers.ts` (`createToolHandlers(ports)`, plus `checkLinesToAdd` for the suggestion card), `cartChanges.ts`, `cartSummary.ts`, `orderType.ts`, `spokenPrice.ts`, `menuSearch.ts`, `tapUpdates.ts`, all free of React and the server. Their tests share `renderedStore()` (`src/agent/testing.ts`, which nothing in the app imports): a real core `ShoppingCart` seen the way a React component sees it, as of the last render. Handlers reach the cart, the screen and checkout only through injected ports, so tests run them against a real core `ShoppingCart` and evals can import them. The React wiring sits beside them in `.tsx` files: `MenuUiProvider`, `OrderTypeProvider`, `CartChangesProvider`, `ToolHandlersProvider`.
- **Every cart change works out the cart after it itself** and summarizes that, since a React component can't read the cart back right after an action (see `LIBRARY_FEEDBACK.md`). The arithmetic is written once, as `CartChange` and `applyCartChange` in `cartSummary.ts`, and the cart changes (`cartChanges.ts`, below) run it for taps and tools alike; it only adds and subtracts, so callers check ids and quantities first. Tests check each kind of change, and every handler summary, against the real store.
- **Several tool calls can run before React re-renders** (Deepgram's `FunctionCallRequest` can carry more than one), while `cartDetails()` still returns the cart from before the first. So the cart changes remember the cart their last change worked out, with the `cartDetails()` object it was based on, and `now()` returns it while `cartDetails()` returns that same object; once a render brings a new object, they trust `cartDetails()` again. It's one memory for taps and tools, so summaries, tap updates and the 20-per-line cap stay right across a batch, and when a tap and a tool call come before the same render. `checkout` reads the rendered cart, since it comes a turn after the customer confirms.
- **Every recovery result is `{ message }`** (`Recovery`, in `src/agent/text.ts` with the `orList` and `andList` the messages and the agent's rules list things with), the same shape `CheckoutResult` uses. `isRecord`, which the handlers, the planner, checkout and the token code all need, is `src/isRecord.ts`. Handlers also take their arguments as the JSON string Deepgram delivers, and a wrapper turns any unexpected error into a message.
- **`set_quantity` and `remove_item` answer an id that isn't in the cart the way SPEC's recovery list does:** an id that isn't on the menu gets what `add_item` would say (close matches, or the size question for a sized item without a size), and an id on the menu but not in the cart gets the cart's lines with their ids, the list the agent needs to retry.
- **Close matches for an unknown id are scored by words:** each word of the id that matches a word in an item's name, id or sizes (equal, a prefix of 4+ letters, or two typos apart for 5+ letters) scores a point, and up to three items with the top score are offered with their variant ids. With no match, the message says nothing is close.
- **`add_items` adds up repeated ids** into one `addItem` call, and the 20-per-line cap counts the sum plus what's in the cart. It checks every line before adding any.
- **`find_menu_items` with no filters returns a message asking for one**, not the whole menu: the agent already has the menu, and lighting up every card says nothing. With `max_price`, only the sizes within it are listed. A query matches when every word appears in the name, description or id.
- **`show_suggestions` checks its lines like `add_items` but not against the cart**, since the cart can change before Add all, which checks again. Repeated ids become one line, a blank title becomes "Suggestions". The card's lines and total come from `summarizeCart`, the one place that prices lines.
- **"Add all of that" by voice closes the suggestion card, as Add all does.** The handlers remember the lines of the last set they showed; when `add_items` succeeds with exactly those lines (same ids and quantities, in any order), they call `closeSuggestions()`, so tapping Add all afterwards can't add the set twice. Any other `add_items` leaves the card open.
- **Tap updates cover add (menu card, Add, Add all), quantity (− and +, with the new quantity) and remove** (`describeTapChange`), and Pickup or Delivery in the cart (`describeOrderTypeTap`, "Customer chose delivery by tapping."). Each says the whole order: a cart change is followed by pickup or delivery ("Order type: delivery.", or "Order type: not chosen yet.") and the cart and total, a choice by the cart and total (for delivery, the total with the fee as well: "Total $46.97, $50.96 with delivery."), then "Call view_cart before answering about the cart." (see the decision on the agent's wording below). After a reconnect the SDK replays only the newest update, so one that left out the choice could undo it. `CartChange` also has `clear`, for the `clear_cart` tool; no tap clears the cart today.
- **Tap updates go to the agent with Deepgram's `UpdatePrompt`.** Its docs (checked 2026-11-10) say it adds to the prompt rather than replacing it; `InjectUserMessage` would make the agent reply and `InjectAgentMessage` would make it speak. Wiring it up is part of the voice half.
- **The page has one set of tool handlers, made by `ToolHandlersProvider` and read with `useToolHandlers()`.** The set remembers whether a voice add has opened the drawer and the suggestions it showed last, so the voice session and the dev tools panel must share it. Its cart port is the page's one set of cart changes, made by `CartChangesProvider`, which reads the cart through a ref updated after each render; the one `eslint-disable` for `react-hooks/refs` there is because the linter can't see that the getter is only called when the cart changes.
- **The Checkout button and the `checkout` tool share `startCheckout`** (`src/checkout/startCheckout.ts`): the server function's answer, or `CHECKOUT_UNAVAILABLE` when the request fails. It never throws, so the tools' `checkout` port is documented as never rejecting and the handler has no try/catch of its own; the handlers' recovering wrapper still answers if a port breaks that promise. The 1–20 quantity rule is `isLineQuantity` in `src/shop.ts`, shared by checkout and the handlers.
- **Any scroll of the page clears the highlights, except the one that brings the first match into view** (`useHighlightScroll`): the wheel, a touch drag, a scroll key, the scrollbar or a category link all count. Scroll events are ignored from the moment the highlight's own scroll starts until it settles (`scrollend`, or 150 ms without a scroll event where `scrollend` is missing or nothing needed scrolling); without that, the smooth scroll would clear the highlights it meant to show. The first match scrolls to the top, just below the sticky header.
- **The suggestion card lives outside the page wrapper and above the cart (z-index 25).** It stays usable while the cart is open: on wide screens it moves to the space beside the drawer, and below 50rem, where there's no room beside it, it hides until the cart closes, so it never covers the Checkout button. It sits above `--voice-space`, the room kept at the bottom for the talk button and, while they show, its captions or message (`--talk-button-space`, plus the captions' room then: see the captions decision), and is at most 60% of the screen tall, with its lines scrolling. When it closes (✕ or Add all), focus goes to the cart's close button while the cart is open, since the page behind it is inert, and to the header's cart button otherwise.
- **Add on a suggestion line can be tapped again, and Add all adds every line,** as SPEC says, even ones already added from the card. A note on the card says what each tap added, or why `checkLinesToAdd` refused it.
- **The dev tools panel lives at `/dev/tools` and exists only in dev.** The route's `beforeLoad` throws `notFound()` unless `import.meta.env.DEV`, and the panel (`src/dev/ToolsPanel.tsx`) loads through `lazy()` only when `import.meta.env.DEV` is true, so a production build drops it and its styles. It renders the same `MenuPage` as `/` (`src/components/MenuPage.tsx`), with the panel as a child inside the tool handlers' provider and outside the inert page wrapper, and calls `useToolHandlers()`, never a second handler set. `src/router.test.ts` checks the 404 outside dev.
- **The panel's styles live next to it, in `src/dev/ToolsPanel.css`,** not in `src/styles.css`, so production builds carry none of them. On phones it's a sheet resting on the talk button's strip (`--voice-space`), so you can talk with it open; from 64rem it's docked on the left and the page and the talk button move over. Open, it sits above the cart and the suggestion card (z-index 30); collapsed, it's a corner tab under the cart (15), so it never covers the Checkout button.
- **The panel's pairings preset reads the cheeseburger's `pairsWith`, and three party presets run `plan_group_order`: 30 people, 10 of them vegetarian (the owner's run), the same on a $250 budget (their next run), and 20 (step 5's Check).** Each is followed by its own Add all of that, which plans the same group again for the cart as it is when tapped, as the handler did, so it adds the lines on the card (the plan leaves room for what's in the cart) and the card closes. The presets show what the menu and the planner say rather than numbers typed by hand.
- **Tap updates go to the agent through the voice session's handle (`tell`, see below), and also to `TapUpdateSinkContext`** (`src/pageContext.ts`), which does nothing by default; the dev tools panel provides one that logs them, with a session or without. `CartChangesProvider` reads the cart once for the whole page, so menu cards don't re-render on every cart change.
- **The agent's instructions and greeting live in `src/agent/instructions.ts`** (`greeting(orderType, tools)`, `agentInstructions(cart, tools, orderType)`, `describeMenu()`), free of React and Deepgram so evals can import them. `{{MENU}}` is one plain-text line per item under a heading per category, each size as `Large: id cheese-pizza-large, $18.99, serves 4.`, all read from `menu.json`; the prompt is about 8,800 characters without tools and 11,000 with them. It ends with `Conversation started. Order type: delivery. Cart: …` (the order type only with `set_order_type` in the session's tools), in the words of `describeOrderType` (`orderType.ts`) and `describeCart` (`cartSummary.ts`), which the tap updates also use, so the updates sent mid-session read as what happened next.
- **The instructions follow the session's tools.** In the owner's second step 4 run the prompt told the agent to use `find_menu_items`, `show_suggestions`, `add_items`, `view_cart` and `checkout` while the session registered none, so it said "Give me a sec" and went silent for 14 s, said "I'll show that now" with nothing shown, and "Adding 5 large pepperoni pizzas … now" three times with nothing added. Now one list drives both: `agentSettings(cart, tools)` sends `tools` as `think.functions` (left out when the list is empty, rather than `[]`, so step 4 sends the request it was tested with) and passes the same list to `agentInstructions(cart, tools)`. A rule that names a tool is kept only when the session has that tool, and some get a version without it. What the agent can't do without its tools (change the cart, show items, check the customer out), a first rule tells it to start by saying it can't do that yet, then point to Add on the menu and Checkout in the cart, all in one sentence, and never say it's adding, showing, checking or looking something up, or that it did (in a later run it answered "add two margheritas" with only "You can tap Add"); without `view_cart` it answers cart questions from the last `Cart:` line and says the cart on screen is the up-to-date one. Every list also gets one rule against stalling ("give me a sec"): do it now with a tool, or answer now. With every tool the rules are the draft above word for word plus that one, which a test checks. Step 4 passes no tools; step 5 passes `toolDefinitions`.
- **The 60-second timeout pauses on the talk button's Speaking status, not on a Deepgram message.** Real sessions on 2026-11-10 never received `AgentStartedSpeaking` (Deepgram's docs no longer list it) or `AgentThinking`, so a pause keyed on them never engaged. The status follows the SDK's mode, which turns to speaking on the agent's first audio chunk and back after `AgentAudioDone` or an interruption (`src/voice/idleTimer.ts`).
- **Voice tokens live 30 seconds** (`TOKEN_TTL_SECONDS` in `src/voice/deepgramToken.ts`, sent as `ttl_seconds`). Deepgram's docs (checked 2026-11-10, https://developers.deepgram.com/reference/auth/tokens/grant) make 30 the default and say a token only has to be valid while the socket opens. `@deepgram/agents` asks for a new token before every connect and reconnect, and gives up on opening after 10 seconds, so 30 covers it. The token server function (`getDeepgramToken`) is a POST, so nothing caches a token, and it answers `{ token }` or `{ message }` the way checkout does.
- **The voice session's lifecycle is one reducer, `updateSession` in `src/voice/sessionStatus.ts`,** free of React and the SDK, so tests run it as lists of events. It owns the talk button's status and message and every rule for ending a session; `VoiceSession.tsx` only turns SDK callbacks into events. A disconnect ends the session ("We lost the connection") only once the agent has its settings and the microphone is on. Before that it's `AgentProvider` hanging up after a failed start, and the error it reports a microtask later says why. The microphone counts too because it starts after the connection opens, so when the browser asks for permission the settings usually arrive first, and a denied prompt would otherwise read as a lost connection.
- **The button shows thinking from the end of the customer's turn until the agent starts speaking.** The SDK's mode turns thinking only on Deepgram's `AgentThinking`, which no session of ours has received, so the button could go straight from listening to speaking. The customer's `ConversationText` (sent at the end of their turn) moves a listening session to thinking in `updateSession`; the agent starting to speak moves it to speaking, and the customer starting again moves it back to listening. A line that arrives after the agent started speaking changes nothing.
- **The session's state lives in `VoiceSessionProvider`, at the top of `MenuPage`,** above `CartChangesProvider` and `ToolHandlersProvider`, so tap updates and voice checkout reach the live session from there (`useVoiceSession()`, below). The talk button, the captions and the per-press `AgentProvider` still render outside the page wrapper an open cart makes inert.
- **The voice agent listens with Flux (`flux-general-en`, `version: 'v2'`), thinks with the Deepgram-managed `open_ai` model `gpt-4.1-mini`, and speaks with Flux TTS (`flux-cole-en`, `version: 'v2'`).** Deepgram's docs (checked 2026-11-10) call Flux "best for low-latency voice agents", with end-of-turn detection built in (https://developers.deepgram.com/docs/voice-agent-stt-models), and Flux TTS "streaming-first, voice-agent-first" (https://developers.deepgram.com/docs/voice-agent-tts-models). They don't recommend an LLM for latency (https://developers.deepgram.com/docs/voice-agent-llm-models); GPT-4.1 mini is a fast managed model that answers without a reasoning step first, and a managed model needs no LLM key or endpoint. All three are set in `agentSettings` (`src/voice/agentSettings.ts`); change the models or the voice there.
- **Captions show the latest exchange, and a toggle opens the whole conversation: "expandable history", which the owner chose on 2026-11-10** over keeping only the latest exchange. By default the captions show the customer's last line and the agent's current reply, as "Voice session" says (`latestExchange` in `src/voice/latestExchange.ts`), so the menu stays visible. The reply is every agent line after the customer's last line, since Deepgram may send a reply as one `ConversationText` or one per sentence; before the customer speaks, it's the greeting. The customer's line keeps its first 2 lines; the agent's reply keeps its newest 3, bottom-aligned with the oldest hidden at the top, because the newest sentence is what the agent is saying now. From the first line, a **Show conversation (N)** toggle (N lines) heads the captions. It opens the session's whole transcript in their place: every line labelled You or Agent, newest at the bottom, in a list that scrolls and follows new lines unless you've scrolled up; **Hide conversation** closes it, and the choice lasts as long as the page (it isn't stored). AgentProvider's conversation goes when its session ends, so `VoiceSession` keeps a copy, the transcript (`src/voice/transcript.ts`, kept by session number). It stays after the session ends, when the captions shrink to the toggle alone and give the menu its room back, until a press starts a new session, which starts a new, empty transcript. Screen readers hear the agent's reply from one polite live region, each line its own span keyed by the line's id, so a new sentence is heard as an addition; while the conversation is open that region stays, visually hidden, and the list isn't a live region, so nothing is read twice. The toggle is a button with `aria-expanded` and `aria-controls` (the list is `hidden` while closed, so it's always there to point to), and the open list can take focus (`tabIndex` 0), so it scrolls from the keyboard; opening it doesn't move focus. Room at the bottom: `--captions-space` (10.5rem) includes the toggle; the open conversation takes `--conversation-space`, at most 16rem or 30% of the screen's height, and never shorter than the collapsed captions (`--captions-space`), so at 360 × 740 the suggestion card above it still shows its lines and Add all, and the full-screen cart its lines, total and Checkout; the toggle alone takes `--toggle-space`. The voice strip never grows past `--voice-space`, so if a message shows under the open conversation, the list gets shorter.
- **While the customer waits for the agent, the captions' last line says what it's doing**, like a typing indicator in a chat: a small spinner and a label where the reply will appear (`src/voice/AgentActivity.tsx`). The owner heard "give me a sec" followed by silence, and a voice UI that looks frozen reads as broken. The line says "Thinking…" while the button shows thinking, and while a tool runs, what it's doing: `find_menu_items` "Searching the menu…", `show_suggestions` "Putting suggestions together…", `plan_group_order` "Planning your order…", `add_item`/`add_items` "Adding to your cart…", `set_quantity`/`remove_item`/`clear_cart` "Updating your cart…", `view_cart` "Checking your cart…", `checkout` "Starting checkout…" (`TOOL_ACTIVITY`, a `Record<ToolName, string>`, so a new tool without a label fails typecheck).
